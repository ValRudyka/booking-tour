Гілка: `feature/frontend-checkout` від актуального `develop` (у цій самій гілці буде й оплата, завдання `05-payment-pages.md`).
Порядок роботи: спочатку план на затвердження, код лише після мого «ок».

Спільні правила — як у `docs/frontend/01-catalog-page.md`, розділи 1–2. Вхід і `RequireAuth` уже є (`03-auth-pages.md`).

1. `docs/tz/TZ_tour_website_v2.md`: процес бронювання (4.4, 4.5), форми заявки й паспортних даних туристів, промокоди (4.6.2.3), модель статусів замовлення (4.4.1), правила утримання місць.
2. Бекенд: checkout з утриманням місць (PR #1–#6), розрахунок ціни, додаткові послуги (страховка, трансфер), перевірка промокоду, створення замовлення, збережені паспорти клієнта (якщо є), строк утримання місць.
3. Документацію antd `Steps`, `Form.List` (динамічні туристи), `DatePicker`.

У плані окремо: послідовність викликів API (що створюється на якому кроці), коли починається й закінчується утримання місць, і **хто рахує підсумкову суму**.

---

## 1. Головне правило: сума рахується лише на сервері

Клієнт не обчислює ціну сам (ні множенням, ні з float). Підсумок, знижки за промокодом, вартість послуг — усе показується з відповіді бекенду. Якщо бекенд має ендпоінт попереднього розрахунку — викликати його при зміні параметрів; якщо ні — у плані запропонувати, як показати суму до підтвердження.

---

## 2. Доступ і вхід

- Маршрут лише для клієнта (`RequireAuth` з роллю клієнта). Гостя кнопка «Забронювати» на сторінці туру тепер веде на `/login?redirect=/booking/:tourId?date=…` (замінити заглушку з `02-tour-details-page.md`).
- Персонал, який відкриває сторінку, бачить 403.

---

## 3. Кроки (`Steps` + `Form`)

```
[1 Дата і туристи] — [2 Дані туристів] — [3 Послуги] — [4 Перевірка]
┌──────────────────────────────────────┬─────────────────────┐
│ Форма поточного кроку                │ Підсумок (SAND_BG)  │
│                                      │ Тур, дата, ночі     │
│                                      │ Туристи: 2 дор.     │
│                                      │ Послуги             │
│                                      │ Промокод [____][ОК] │
│                                      │ Разом: N ₴          │
│ [Назад]                    [Далі]    │ (з сервера)         │
└──────────────────────────────────────┴─────────────────────┘
```

На мобільному підсумок згортається над кнопками (`Collapse` або коротка панель «Разом: N ₴»).

### Крок 1. Дата і туристи
- Дата виїзду (попередньо обрана з `?date=` зі сторінки туру), місто вильоту, якщо їх кілька.
- Кількість дорослих і дітей (`InputNumber`), з урахуванням вільних місць і правил бекенду.
- Якщо місць не вистачає — пояснення біля поля, кнопка «Далі» не пускає далі.

### Крок 2. Дані туристів
- `Form.List`: блок на кожного туриста — поля з форми паспортних даних ТЗ, які приймає API (прізвище й ім'я латиницею як у закордонному паспорті, дата народження, стать, громадянство, номер і строк дії паспорта).
- Перший турист — «Заповнити з мого профілю», якщо в API є дані клієнта; збережені паспорти (якщо є в API) — вибір із `Select`.
- Перевірки: латиниця в іменах; строк дії паспорта не раніше дати повернення (якщо бекенд має таке правило — показувати його помилку); вік дитини відповідає позначці «дитина».
- Помилки 422 з бекенду — біля конкретного поля конкретного туриста.

### Крок 3. Послуги
- Страховка, трансфер та інші послуги, які повертає API (`Checkbox` / `Radio.Group` з ціною кожної, ціни з сервера).
- Промокод: поле й кнопка «Застосувати»; результат перевірки (знижка або причина відмови) з сервера.

### Крок 4. Перевірка
- `Descriptions` з усіма даними: тур, дати, туристи (паспортні номери частково приховані: `AB****56`), послуги, промокод, підсумок.
- `Checkbox` згоди з умовами договору (обов'язковий).
- Кнопка «Підтвердити й перейти до оплати» створює замовлення (якщо воно ще не створене) і веде на оплату (`05-payment-pages.md`). Повторне натискання не створює друге замовлення (кнопка блокується під час запиту; якщо бекенд підтримує ключ ідемпотентності — використати).

---

## 4. Утримання місць

- Якщо бекенд утримує місця на час оформлення — показувати над формою `Alert`: «Місця утримуються до 14:35 (залишилось 12 хв)». Текст оновлюється раз на хвилину (без анімації), за останні 2 хвилини — щосекунди.
- Час береться з відповіді API (`expires_at` чи аналог), а не рахується від моменту відкриття сторінки.
- Після закінчення: `Result` «Час утримання місць минув» з кнопкою «Почати знову» (заново перевіряє наявність).
- Дані форми не губляться при переході між кроками й при випадковому оновленні сторінки (зберігати чернетку в `sessionStorage`, але **без паспортних номерів** — їх просто доведеться ввести заново).

---

## 5. Стани

| Стан | Що показати |
|---|---|
| Тур не продається / немає місць | `Result` з поясненням і кнопкою «До каталогу» |
| Конфлікт (409) при створенні замовлення, напр. місця щойно закінчились | `Alert` з текстом від бекенду і поверненням на крок 1 |
| Помилка мережі | `Alert` з кнопкою повтору; введені дані залишаються |
| Режим обслуговування | Той самий компонент, що в каталозі |

---

## 6. Тести (у тих самих комітах, що й код)

- Гість перенаправляється на вхід з правильним `redirect`.
- Перехід між кроками зберігає дані; «Далі» не пропускає з помилками.
- Сума в підсумку береться з відповіді мок-API, а не рахується на клієнті.
- Промокод: успіх і відмова показують текст сервера.
- Закінчення утримання показує `Result`.
- Подвійне натискання «Підтвердити» робить один запит.
- 422 по туристу з'являється біля його поля.
