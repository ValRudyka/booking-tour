# Туристичний вебсайт

Курсовий проєкт: вебсайт туристичної компанії з каталогом турів, онлайн-бронюванням,
оплатою (Stripe, тестовий режим), обробкою заявок менеджером, поверненням коштів і відгуками.
Вимоги — у Технічному завданні: `docs/tz/TZ_tour_website_v2.md`
(офіційний документ — `docs/tz/TZ_tour_website_v2.docx`).

| Частина  | Технології                                                          |
| -------- | ------------------------------------------------------------------- |
| Backend  | Python 3.12, FastAPI, SQLAlchemy 2.0 (sync), Alembic, PostgreSQL 16 |
| Frontend | React, TypeScript, Vite, Tailwind CSS, react-i18next _(з етапу 5)_  |
| Тести    | pytest                                                              |

│   │   └── core/          # безпека: JWT, паролі, ролі
│   ├── alembic/versions/  # міграції БД (джерело правди про схему)

## Перший запуск (Windows)

### 1. База даних (pgAdmin)

1. Підключіться до сервера як `postgres`, відкрийте **Query Tool** на базі `postgres`.
2. Відкрийте `database/01_create_roles_and_databases.sql`, **замініть пароль**
   і виконайте **три блоки по черзі** (виділити блок → F5).
3. У дереві pgAdmin натисніть _Refresh_, з'являться бази `tour_website` і `tour_website_test`.

Далі таблиці можна створити **одним із двох способів** (обидва дають однаковий результат):

- **Спосіб А — Alembic (рекомендовано):** див. крок 3 нижче, команда `alembic upgrade head`.
- **Спосіб Б — SQL-скрипти в pgAdmin:** створіть у pgAdmin нове підключення до бази
  `tour_website` **від імені користувача `tour_app`** і виконайте по черзі
  `database/02_schema.sql`, потім `database/03_reference_data.sql`, потім
  `database/05_order_number_sequence.sql`.
  Скрипти також записують версію в таблицю `alembic_version`, тож надалі
  нові міграції застосовуються звичайною командою `alembic upgrade head`.

### 2. Python-середовище

```bash
conda create -n tour python=3.12
conda activate tour
cd backend
pip install -r requirements.txt
copy .env.example .env      # і впишіть свій пароль у DATABASE_URL та TEST_DATABASE_URL
```

### 3. Міграції, тести, запуск

```bash
alembic upgrade head        # створює/оновлює таблиці (пропустіть, якщо виконали спосіб Б)
pytest                      # тести працюють з базою tour_website_test
uvicorn app.main:app --reload
```

`pytest` бере `TEST_DATABASE_URL` зі змінних середовища або з `backend/.env`,
тож його можна запускати як з `backend/`, так і з кореня репозиторію.
Дані тестової бази **видаляються** при кожному запуску — ніколи не вказуйте там основну базу.

- API: http://127.0.0.1:8000
- Документація Swagger: http://127.0.0.1:8000/docs
- Перевірка: http://127.0.0.1:8000/health → `{"status":"ok","database":"ok"}`

## Автентифікація та ролі

- `POST /api/auth/register` — реєстрація клієнта (роль завжди `client`).
- `POST /api/auth/login` — вхід: поле `username` = телефон **або** e-mail, `password`.
  Повертає JWT (`access_token`), який передається в заголовку `Authorization: Bearer <token>`.
  У Swagger (`/docs`) — кнопка **Authorize**.
- `GET/PATCH /api/auth/me`, `POST /api/auth/me/password` — профіль і зміна пароля.

Паролі зберігаються як хеш **Argon2id** (бібліотека `pwdlib`), токени — **PyJWT** (HS256),
як рекомендує документація FastAPI. Ролі перевіряє залежність `require_roles(...)` (`app/core/deps.py`).

Співробітники (менеджер, фінансовий контролер, адміністратор) не реєструються самі —
їх створює скрипт:

```bash
python -m scripts.create_user --role admin --phone +380500000001 \
    --email admin@tour.local --password "Admin-pass-1" --last-name Адмін --first-name Системний
```

Ролі: `client`, `manager`, `finance`, `admin`.

## Тури та каталог

**Менеджер** (лише роль `manager`, префікс `/api/manager/tours`) — форма 4.6.2.1 ТЗ:

- `POST /` — створити тур (завжди «Чернетка»); якщо назва українською порожня, вона
  формується як «Готель, Курорт». Програма туру — масив `program_days`.
- `GET /`, `GET /{id}` — список усіх турів (фільтр `status`, пошук `q`) і тур для редагування.
- `PATCH /{id}` — редагувати можна **лише чернетку** (ТЗ 4.4.1: активний тур спершу
  повертають у чернетку).
- `POST /{id}/publish`, `/unpublish`, `/archive` — статуси «Чернетка» ↔ «Активний» → «Архівний».
  Кожна зміна статусу пишеться в `audit_log`.
- `POST /{id}/copy` — копія туру як нова чернетка (разом із програмою та фото).
- `POST /{id}/images` (multipart, поле `files`), `DELETE /{id}/images/{image_id}`,
  `PUT /{id}/images/order` — фото JPG/PNG, до 5 МБ, до 20 на тур. Тип визначається за
  вмістом файлу, а ім'я файлу на диску генерує сервер. Фото лежать у `backend/uploads/tours/`
  і віддаються за адресою `/uploads/tours/...`. Публічна **лише** папка `tours`: документи
  замовлень та інші особисті файли зберігатимуться поза нею й видаватимуться тільки через
  API з перевіркою прав.

**Публічно, без входу:**

- `GET /api/tours` — каталог активних турів: `q`, `country_id`, `resort_id`,
  `departure_city_id`, `transport_type`, `date_from`/`date_to`, `nights_min`/`nights_max`,
  `price_min`/`price_max` (у гривнях), `stars` (можна кілька), `featured`, `has_seats`;
  `sort` = `price_asc|price_desc|date_asc|date_desc|rating_desc`; `page`, `page_size` (до 50).
- `GET /api/tours/{id}` — сторінка туру: ціна «від X грн», вільні місця, програма, фото.
- `GET /api/reference/countries|resorts|hotels|cities` — довідники для фільтрів.

Ціна в гривнях = базова вартість × комерційний курс (`currency_rates`).
Вільні місця = квота − продані − місця в неістеклих утриманнях (утримання з'являться з чекаутом).

**Демо-дані.** Готелі веде адміністратор (етап 8); поки його немає, каталог можна заповнити:

```bash
python -m scripts.create_user --role manager --phone +380500000002     --email manager@tour.local --password "Manager-pass-1" --last-name Менеджер --first-name Демо
python -m scripts.seed_demo   # 5 готелів і 4 опубліковані тури; повторний запуск нічого не дублює
```

## Замовлення (чекаут)

Лише роль `client`, лише свої замовлення (чуже замовлення → 404). Сценарій 4.5.3, форма 4.6.1.2.

- `POST /api/orders/quote` — розрахунок вартості без збереження (розбивка: тур, страховка,
  трансфер, знижка, разом).
- `POST /api/orders` — «Забронювати»: номер `TU-2026-000123`, статус «Оформлення», місця
  утримуються на `booking_timeout_min` хвилин (налаштування, за замовчуванням 20).
  Таймер не продовжується жодними змінами.
- `PATCH /api/orders/{id}` — туристи, кількість, страховка, трансфер, промокод, побажання
  (лише в статусі «Оформлення»); ціна перераховується.
- `POST /api/orders/{id}/confirm` — «Перейти до оплати»: потрібна згода з офертою
  (`accept_offer: true`), дані всіх туристів; ціна й курс фіксуються → «Очікує оплати».
- `POST /api/orders/{id}/cancel` — скасувати неоплачене замовлення; місця звільняються.
- `GET /api/orders`, `GET /api/orders/{id}` — мої замовлення та історія статусів.
- `GET/POST/DELETE /api/me/passports` — збережені паспорти для автозаповнення.
- `GET /api/reference/insurance-types`, `/transfer-types` — додаткові послуги.

Правила:
- Ціна = (база × дорослі + дитяча × діти) × курс + страховка × туристи + трансфер − знижка.
  Дитина — до 12 років на дату заїзду (визначається з дати народження).
- Паспорт має діяти щонайменше 6 місяців після повернення; імена — латиницею.
- Промокод: активний, у межах дат, сума від мінімальної, ліміт не вичерпано.
- Замовлення, у яких минув час утримання, сервер скасовує щохвилини (від імені Системи);
  вручну: `python -m scripts.expire_orders`.

## База даних

27 таблиць, 37 зв'язків, 34 іменовані CHECK-обмеження. Схема описана в `app/models/`,
усі зміни — тільки через міграції:

```bash
# після зміни моделей
alembic revision --autogenerate -m "опис зміни"
alembic upgrade head
alembic check                 # перевірка: моделі і БД збігаються

# оновити ER-діаграму з моделей
python -m scripts.generate_er # -> docs/er_diagram.puml

# оновити SQL-скрипти для pgAdmin
alembic upgrade base:head --sql > ../database/schema_full.sql
```

Статуси замовлення, оплати та туру відповідають розділу 4.4.1 ТЗ
(`app/models/enums.py`). Значення зберігаються як `VARCHAR` + `CHECK`,
тому база сама відхиляє невідомий статус.
