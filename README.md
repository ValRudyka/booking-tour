# Туристичний вебсайт

Курсовий проєкт: вебсайт туристичної компанії з каталогом турів, онлайн-бронюванням,
оплатою (Stripe, тестовий режим), обробкою заявок менеджером, поверненням коштів і відгуками.
Вимоги — у Технічному завданні: `docs/tz/TZ_tour_website_v2.md`
(офіційний документ — `docs/tz/TZ_tour_website_v2.docx`).

| Частина  | Технології                                                                                   |
| -------- | -------------------------------------------------------------------------------------------- |
| Backend  | Python 3.12, FastAPI, SQLAlchemy 2.0 (sync), Alembic, PostgreSQL 16                          |
| Frontend | React 19, TypeScript 6, Vite 8, antd 6 (+ pro-components для бекофісу), React Router, TanStack Query, react-i18next |
| Тести    | pytest (672 тести backend), Vitest + Testing Library (163 тести frontend)                    |

## Перший запуск (Windows)

### 1. База даних (pgAdmin)

1. Підключіться до сервера як `postgres`, відкрийте **Query Tool** на базі `postgres`.
2. Відкрийте `database/01_create_roles_and_databases.sql`, **замініть пароль**
   і виконайте **три блоки по черзі** (виділити блок → F5).
3. У дереві pgAdmin натисніть _Refresh_, з'являться бази `tour_website` і `tour_website_test`.

Далі таблиці можна створити **одним із двох способів** (обидва дають однаковий результат):

- **Спосіб А — Alembic (рекомендовано):** див. крок 3 нижче, команда `alembic upgrade head`.
- **Спосіб Б — SQL-скрипти в pgAdmin:** створіть у pgAdmin нове підключення до бази
  `tour_website` **від імені користувача `tour_app`** і виконайте по черзі
  `database/02_schema.sql`, потім `database/03_reference_data.sql`, потім
  `database/05_order_number_sequence.sql`, потім `database/06_bank_transfer_hold_setting.sql`,
  потім `database/07_refunds_and_cancellation.sql`, потім `database/08_review_moderation.sql`, потім `database/09_admin.sql`,
  потім `database/10_resort_alanya_spelling.sql`, потім `database/11_catalog_improvements.sql`.
  Скрипти також записують версію в таблицю `alembic_version`, тож надалі
  нові міграції застосовуються звичайною командою `alembic upgrade head`.

> **Потрібен PostgreSQL з підтримкою ICU.** Сортування турів за назвою (А–Я) використовує
> колацію `uk-x-icu`, щоб Є, І, Ї та Ґ стояли на своїх місцях в українському алфавіті.
> Інсталятор PostgreSQL для Windows і офіційні Docker-образи `postgres` її мають; перевірка:
> `SELECT collname FROM pg_collation WHERE collname = 'uk-x-icu';`. На сервері без ICU міграція
> `c3d8a1f5b742` (і скрипт `11`) зупиняється з поясненням — це варто пам'ятати при розгортанні.

### 2. Python-середовище

```bash
conda create -n tour python=3.12
conda activate tour
cd backend
pip install -r requirements.txt
copy .env.example .env      # і впишіть свій пароль у DATABASE_URL та TEST_DATABASE_URL
```

### 3. Міграції, тести, запуск

```bash
alembic upgrade head        # створює/оновлює таблиці (пропустіть, якщо виконали спосіб Б)
pytest                      # тести працюють з базою tour_website_test
uvicorn app.main:app --reload
```

`pytest` бере `TEST_DATABASE_URL` зі змінних середовища або з `backend/.env`,
тож його можна запускати як з `backend/`, так і з кореня репозиторію.
Дані тестової бази **видаляються** при кожному запуску — ніколи не вказуйте там основну базу.

- API: http://127.0.0.1:8000
- Документація Swagger: http://127.0.0.1:8000/docs
- Перевірка: http://127.0.0.1:8000/health → `{"status":"ok","database":"ok"}`

## Автентифікація та ролі

- `POST /api/auth/register` — реєстрація клієнта (роль завжди `client`). Обов'язкові: телефон
  у міжнародному форматі (`+` і 10–15 цифр, будь-яка країна), e-mail, пароль 8–128 символів,
  прізвище й ім'я (громадяни України — українськими літерами, інших держав — латиницею),
  **дата народження (від 18 років за київською датою)** і **громадянство**, згода на обробку
  даних. Токена не повертає — фронтенд одразу виконує вхід. E-mail на службових доменах
  (`.local`, `.test` тощо) валідатор не приймає.
- `POST /api/auth/login` — вхід: поле `username` = телефон **або** e-mail, `password`.
  Повертає JWT (`access_token`), який передається в заголовку `Authorization: Bearer <token>`.
  У Swagger (`/docs`) — кнопка **Authorize**.
- `GET/PATCH /api/auth/me`, `POST /api/auth/me/password` — профіль і зміна пароля.

Паролі зберігаються як хеш **Argon2id** (бібліотека `pwdlib`), токени — **PyJWT** (HS256),
як рекомендує документація FastAPI. Ролі перевіряє залежність `require_roles(...)` (`app/core/deps.py`).

Співробітники (менеджер, фінансовий контролер, адміністратор) не реєструються самі — їх
створює адміністратор (`POST /api/admin/users`, див. «Адміністрування»). Першого адміністратора
створює скрипт:

```bash
python -m scripts.create_user --role admin --phone +380500000001 \
    --email admin@tour.local --password "Admin-pass-1" --last-name Адмін --first-name Системний
```

Ролі: `client`, `manager`, `finance`, `admin`.

## Тури та каталог

**Менеджер** (лише роль `manager`, префікс `/api/manager/tours`) — форма 4.6.2.1 ТЗ:

- `POST /` — створити тур (завжди «Чернетка»); якщо назва українською порожня, вона
  формується як «Готель, Курорт». Програма туру — масив `program_days`.
- `GET /`, `GET /{id}` — список усіх турів (фільтр `status`, пошук `q`) і тур для редагування.
- `PATCH /{id}` — редагувати можна **лише чернетку** (ТЗ 4.4.1: активний тур спершу
  повертають у чернетку).
- `POST /{id}/publish`, `/unpublish`, `/archive` — статуси «Чернетка» ↔ «Активний» → «Архівний».
  Кожна зміна статусу пишеться в `audit_log`.
- `POST /{id}/copy` — копія туру як нова чернетка (разом із програмою та фото).
- `POST /{id}/images` (multipart, поле `files`), `DELETE /{id}/images/{image_id}`,
  `PUT /{id}/images/order` — фото JPG/PNG, до 5 МБ, до 20 на тур. Тип визначається за
  вмістом файлу, а ім'я файлу на диску генерує сервер. Фото лежать у `backend/uploads/tours/`
  і віддаються за адресою `/uploads/tours/...`. Публічна **лише** папка `tours`: документи
  замовлень та інші особисті файли зберігатимуться поза нею й видаватимуться тільки через
  API з перевіркою прав.

**Публічно, без входу:**

- `GET /api/tours` — каталог турів, які ще продаються (активні й мають дату заїзду **від завтра**
  за київським часом — найранішу дату, яку приймає бронювання): `q`, `country_id`, `resort_id`,
  `departure_city_id`, `transport_type`, `date_from`/`date_to`, `nights_min`/`nights_max`,
  `price_min`/`price_max` (у гривнях), `stars` і `meal_plan` (можна кілька: `meal_plan=ai&meal_plan=uai`),
  `featured`, `has_seats`; `sort` = `price_asc|price_desc|date_asc|date_desc|rating_desc|title_asc`
  (`title_asc` — за українським алфавітом); `page`, `page_size` (до 50). У картці — тип харчування.
- `GET /api/tours/{id}` — сторінка туру: ціна «від X грн», вільні місця, програма, фото,
  «Що включено / не включено», готель з фактами (лінія пляжу, відстані, заїзд/виїзд, зручності,
  типи номерів). Тур, який більше не продається, — 404.

**Тип харчування** (`ro`, `bb`, `hb`, `fb`, `ai`, `uai`) належить туру, а не готелю: той самий
готель продається з різним харчуванням. Страхування й трансфер ніколи не потрапляють у «Що
включено» — клієнт обирає й оплачує їх під час бронювання. Факти про готель редагує
адміністратор у довіднику готелів (форма 4.6.4.2).

**Дати:** «сьогодні» для всієї системи — дата в Києві (`services/clock.py`), а не дата сервера чи
UTC: каталог, бронювання, промокоди, паспорти, а також фільтри за датами в реєстрі платежів і
журналі змін (дні рахуються за київським часом).
- `GET /api/reference/countries|resorts|hotels|cities` — довідники для фільтрів.

Ціна в гривнях = базова вартість × комерційний курс (`currency_rates`).
Вільні місця = квота − продані − місця в неістеклих утриманнях (утримання з'являться з чекаутом).

## Демо-дані

Лише для розробки: каталог для перевірки фільтрів і пагінації. Скрипт працює, тільки якщо в
`backend/.env` є `APP_ENV=development` (за замовчуванням `production`) і ключ Stripe не `sk_live_`.

```bash
alembic upgrade head                      # потрібні всі міграції (зокрема поля харчування й готелів)
python -m scripts.seed_demo               # створити те, чого бракує; повторний запуск нічого не дублює
python -m scripts.seed_demo --reset       # прибрати лише те, що створив скрипт
python -m scripts.seed_demo --remove-legacy   # прибрати старі демо-готелі v1 (реальні назви)
```

**Оновлення вже заповненої бази.** Скрипт ніколи не змінює вже створені записи, тому щоб
отримати нові демо-дані (факти готелів, харчування, фото, відгуки) на базі, заповненій старішою
версією, виконайте по черзі `python -m scripts.seed_demo --reset` і `python -m scripts.seed_demo`.

- Дані — `backend/scripts/data/hotels_uk.json` (10 вигаданих готелів з фактами: лінія пляжу,
  відстані, заїзд/виїзд, зручності, типи номерів) і `tours_uk.json`: 28 турів (25 активних,
  2 чернетки, 1 архівний, 6 «Гарячих пропозицій», 1 тур з одним вільним місцем); харчування туру
  береться з його готелю; «Що включено / не включено» — типові списки за видом транспорту.
  Промокоди `DEMO10` (−10 %) і `DEMO1500` (−1500 грн від 30 000 грн). Лише українською
  (`title_en` поки дорівнює українській назві).
- **Фото:** по 3 на тур, генеруються локально (`scripts/placeholder_images.py`, PNG без Pillow і
  без завантажень з інтернету).
- **Поїздки, що вже відбулися:** 3 тури «на весь сезон» почалися в минулому й ще продаються.
  На них 4 заблоковані демо-клієнти з вигаданими іменами мають 9 завершених замовлень: усі
  статуси, квота й історія — через звичайні сервіси. До кожного є опублікований відгук, а до 7 з
  них — фото, тож у трьох готелів з'являється рейтинг.
- **Демо-оплати не є грошима:** у таблиці `payments` вони мають `origin = demo_seed` (звичайні —
  `app`). Реєстр платежів фінансового контролера показує це поле й фільтрує за ним
  (`GET /api/finance/payments?origin=app` — без демо-даних); звіти мають брати лише `app`.
- Курорти Салоу та Золоті Піски створюються тим самим сервісом, що й в адміністратора.
- Записи підписані заблокованими обліковими записами «Демо-дані» (адміністратор, менеджер і
  4 клієнти), а фото турів — записом «tour_image created» у журналі змін, тому `--reset` знає, що
  створив сам. Він видаляє замовлення демо-клієнтів з оплатами, відгуками, файлами фото й
  сповіщеннями (кожне видалення — у журналі змін; сам застосунок замовлень ніколи не видаляє),
  перераховує рейтинги та повертає місця в квоту, якщо тур лишається. Тур із чужими
  замовленнями, відгуками, обраним чи фото, завантаженими вручну, не видаляється, а архівується;
  готель або курорт, які ще використовуються, лишаються.

## Замовлення (чекаут)

Лише роль `client`, лише свої замовлення (чуже замовлення → 404). Сценарій 4.5.3, форма 4.6.1.2.

- `POST /api/orders/quote` — розрахунок вартості без збереження (розбивка: тур, страховка,
  трансфер, знижка, разом).
- `POST /api/orders` — «Забронювати»: номер `TU-2026-000123`, статус «Оформлення», місця
  утримуються на `booking_timeout_min` хвилин (налаштування, за замовчуванням 20).
  Таймер не продовжується жодними змінами.
- `PATCH /api/orders/{id}` — туристи, кількість, страховка, трансфер, промокод, побажання
  (лише в статусі «Оформлення»); ціна перераховується.
- `POST /api/orders/{id}/confirm` — «Перейти до оплати»: потрібна згода з офертою
  (`accept_offer: true`), дані всіх туристів; ціна й курс фіксуються → «Очікує оплати».
- `POST /api/orders/{id}/cancel` — скасувати неоплачене замовлення; місця звільняються.
- `GET /api/orders`, `GET /api/orders/{id}` — мої замовлення та історія статусів.
- `GET/POST/DELETE /api/me/passports` — збережені паспорти для автозаповнення.
- `GET /api/reference/insurance-types`, `/transfer-types` — додаткові послуги.

Правила:
- Ціна = (база × дорослі + дитяча × діти) × курс + страховка × туристи + трансфер − знижка.
  Дитина — до 12 років на дату заїзду (визначається з дати народження).
- Паспорт має діяти щонайменше 6 місяців після повернення; імена — латиницею.
- Промокод: активний, у межах дат, сума від мінімальної, ліміт не вичерпано.
- Замовлення, у яких минув час утримання, сервер скасовує щохвилини (від імені Системи);
  вручну: `python -m scripts.expire_orders`.

## Оплата

`POST /api/orders/{id}/pay` (власник замовлення в статусі «Очікує оплати»):

- `{"method": "card"}` — платіж «очікує» і сесія **Stripe Checkout** (тестовий режим) у гривнях;
  у відповіді `checkout_url`, куди перенаправити клієнта. Повторний виклик повертає ту саму
  відкриту сесію. Сума менша за мінімум Stripe (≈ 17 грн) → 409; сума 0 (промокод покрив
  усе) → замовлення одразу «Оплачено».
- `{"method": "bank_transfer"}` — реквізити й призначення платежу з номером замовлення;
  утримання місць один раз продовжується на `bank_transfer_hold_hours` (налаштування, 48 год).

Оплату карткою зараховує **лише вебхук** Stripe з перевіреним підписом
(`POST /api/payments/stripe/webhook`), а не сторінка повернення. Повторні події нічого не
змінюють. Якщо гроші прийшли для вже скасованого замовлення або місць більше немає, Система
автоматично повертає їх через Refund API (рядок `refund` у платежах), статус замовлення не змінюється.
Коли утримання минає, відкрита сесія Stripe закривається через API.

Фінансовий контролер (роль `finance`, форма 4.6.3.1):
- `GET /api/finance/payments` — реєстр: фільтри `status`, `method`, `type`, `date_from`/`date_to`, `order_number`;
- `POST /api/finance/payments/{id}/confirm` (multipart): `paid_amount`, `received_at`, `purpose`,
  `comment`, файл `statement` (PDF/JPG/PNG). Неповна сума → «Сплачено частково», новий платіж
  на залишок, утримання продовжується; повна → «Оплачено»;
- `GET /api/finance/payments/{id}/statement` — виписка (зберігається поза публічною папкою).

**Без Stripe** (`PAYMENT_GATEWAY=mock` або порожній ключ) `checkout_url` веде на тестову
сторінку `/api/payments/mock/{session_id}` з кнопками «Оплата успішна» / «Сесія минула».

**Зі Stripe** (тестові ключі в `backend/.env`, див. `.env.example`), в окремому терміналі
(PowerShell; список подій — у лапках):

```powershell
stripe listen --events "checkout.session.completed,checkout.session.expired,checkout.session.async_payment_succeeded,checkout.session.async_payment_failed,refund.updated,refund.failed" --forward-to 127.0.0.1:8000/api/payments/stripe/webhook
```

Команда друкує `whsec_...` — впишіть його в `STRIPE_WEBHOOK_SECRET` і перезапустіть сервер.
Тестова картка: `4242 4242 4242 4242`, будь-яка майбутня дата й CVC. Для перевірки повернень:
`4000 0000 0000 7726` — повернення спершу «очікує», потім успішне (`refund.updated`);
`4000 0000 0000 5126` — повернення спершу успішне, а за кілька хвилин не вдається (`refund.failed`).

## Обробка заявок, документи, скасування та повернення

**Менеджер** (роль `manager`, префікс `/api/manager/orders`) — сценарії 4.5.4, 4.5.9, форма 4.6.2.2:

- `GET /` — «Вхідні заявки»: фільтри `status` (можна кілька), `tour_id`, `start_from`/`start_to`,
  `number`, `mine` (я відповідальний), `overdue` (дата туру настала, а документів немає);
  архівні замовлення приховані, доки не вибрано `status=archived`.
- `GET /{id}` — заявка: туристи з паспортними даними (лише для співробітників і самого клієнта),
  платежі, документи, історія статусів, внутрішній коментар.
- `POST /{id}/take` — «Взяти в роботу»: «Оплачено» → «В роботі», менеджер стає відповідальним.
  Після цього змінювати замовлення може **лише він** (інший менеджер отримує 409), переглядати —
  будь-який. `POST /{id}/assign` (`manager_id`) — передати замовлення іншому менеджеру.
- `POST /{id}/confirm` — PNR і дедлайн оплати туроператору → «Підтверджено».
- `POST /{id}/reject` — причина → «Відхилено»: місця повертаються до квоти, замовлення потрапляє
  до черги повернень фінансового контролера (повне повернення).
- `POST /{id}/documents` (multipart: `doc_type` = `voucher|air_ticket|insurance_policy|info_sheet`,
  `files`), `DELETE /{id}/documents/{doc_id}`, `GET /{id}/documents/{doc_id}/download` —
  PDF/JPG/PNG до `MAX_DOCUMENT_MB` (10 МБ). Файли зберігаються **приватно**
  (`uploads/private/orders/...`), а не в публічній папці.
- `POST /{id}/documents-ready` — «Документи готові» (потрібен хоча б один ваучер).
- `PATCH /{id}` — лише `internal_comment` (клієнт його не бачить).
- `POST /{id}/archive` — «Архівний» із «Завершено», «Відхилено», «Скасовано»; два останні —
  лише після завершення повернення коштів.

До `confirm`, `reject`, `documents-ready` можна додати `client_message` — текст для клієнта (поле 7).

**Клієнт** (лише свої замовлення):

- `GET /api/orders/{id}/documents`, `GET /api/orders/{id}/documents/{doc_id}/download` — документи
  на подорож, починаючи зі статусу «Підтверджено». Чужий документ → 404.
- `POST /api/orders/{id}/cancel-request` (multipart, форма 4.6.1.3): `reason_code`
  (`illness|change_of_plans|data_error|visa_refusal|other`), `details`, `accept_penalty_policy=true`
  (згода з утриманням ФПВ), до 5 довідок PDF/JPG. Можна з «Оплачено», «В роботі», «Підтверджено»,
  «Документи готові» → «Очікує скасування». Неоплачене замовлення скасовується одразу (`/cancel`).
- `GET /api/me/notifications` (`unread_only`), `POST /api/me/notifications/{id}/read`, `/read-all` —
  сповіщення в Особистому кабінеті (для будь-якої ролі): оплачено, підтверджено, документи готові,
  відхилено, скасовано, кошти повернено, подорож завершено. E-mail — окремий етап.

**Фінансовий контролер** (роль `finance`, сценарій 4.5.6, форма 4.6.3.1):

- `GET /api/finance/refunds` — черга: клопотання про скасування, відхилені замовлення з
  неповерненими коштами, невдалі повернення, повернення, що очікують Stripe, і частково оплачені
  переказом замовлення, за якими клієнт не доплатив вчасно.
- `GET /api/finance/orders/{id}`, `.../documents/{doc_id}/download` — замовлення та довідки клієнта.
- `POST /api/finance/orders/{id}/refund` (multipart): `fpv_amount` (ФПВ; для відхилених — 0),
  `comment` (обов'язковий, якщо ФПВ > 0), для переказу — `transfer_sent_at`, `transfer_details`,
  `statement`; `manual=true` — повернути картковий платіж переказом, якщо Stripe не зміг.

Як рахується повернення: сума успішних платежів − уже повернене − ФПВ. Вона розподіляється по
платежах **від найновішого**: картка повертається через Stripe Refund API (часткові повернення
дозволені, ключ ідемпотентності `refund-<платіж>-<n>`), банківський переказ фіксується вручну з
реквізитами й квитанцією. Якщо Stripe відмовив на другій частині, коли першу вже повернено, база
нічого не зберігає, а відповідь 502 просить **повторити той самий запит**: ті самі ключі
повертають уже створені повернення, тож гроші не повертаються двічі. Коли все повернено:
статус оплати «Повернено» / «Повернено частково», «Очікує скасування» → «Скасовано» (місця
повертаються), відхилене замовлення лишається «Відхилено». Повернення, яке Stripe ще обробляє,
завершує вебхук `refund.updated`; `refund.failed` повертає замовлення до черги.

**Система:** замовлення «Документи готові» стають «Завершено» наступного дня після дати
повернення (за київським часом) — сервер перевіряє щогодини (`ORDER_COMPLETION_INTERVAL_SEC`),
вручну: `python -m scripts.complete_orders`. Замовлення, що так і не отримали документів
(«Оплачено», «В роботі», «Підтверджено»), автоматично не завершуються: вони потрапляють у
фільтр `overdue=true`, і менеджер вирішує — завантажити документи чи відхилити з поверненням.

## Відгуки та рейтинг

Сценарій 4.5.7, форма 4.6.1.4. Після «Завершено» клієнт отримує сповіщення з запрошенням залишити відгук.

**Клієнт** (лише свої замовлення):

- `POST /api/orders/{id}/review` (multipart): `hotel_rating` і `service_rating` (1–5, обов'язкові),
  `positive`, `negative` (необов'язкові), `name_display` = `full|short|anonymous`, до 10 фото
  `photos` (JPG/PNG, до `MAX_REVIEW_PHOTO_MB` = 5 МБ кожне). Лише для замовлень «Завершено»
  (або «Архівний» після «Завершено»), один відгук на замовлення.
- `GET /api/me/reviews` — мої відгуки: статус модерації, причина відхилення, `can_resubmit`.
- `PATCH /api/me/reviews/{id}` — **один раз** виправити відхилений відгук і подати знову
  (передані поля змінюються; нові фото замінюють старі, `clear_photos=true` — прибрати всі).

**Модерація** (роль `manager`, префікс `/api/manager/reviews`): `GET /` — черга (за замовчуванням
`status=pending`, найстаріші спочатку; фільтри `tour_id`, `hotel_id`), `GET /{id}`,
`POST /{id}/publish`, `POST /{id}/reject` (`reject_reason` обов'язкова; опублікований відгук так
знімається з публікації). Клієнт отримує сповіщення про рішення. Текст відгуку співробітники не
редагують. Налаштування `review_premoderation` (таблиця `settings`, за замовчуванням `true`):
якщо `false`, відгук публікується одразу.

**Рейтинг:** `hotels.rating_avg` = середня оцінка готелю за опублікованими відгуками (2 знаки,
`NULL`, якщо відгуків немає), перераховується в тій самій транзакції, що й публікація / зняття.
За ним працює сортування каталогу `sort=rating_desc`. Сторінка туру показує `reviews_count` і
`service_rating_avg`.

**Публічно, без входу:** `GET /api/tours/{id}/reviews`, `GET /api/hotels/{id}/reviews` — лише
опубліковані, нові спочатку. Автор — «Олена Коваль», «Олена К.» або «Анонімний мандрівник»;
жодних телефонів, e-mail, номерів замовлень. Фото — `GET /api/reviews/{id}/photos/{photo_id}`:
зберігаються приватно; опублікованого відгуку бачать усі, неопублікованого — лише автор і
менеджери (іншим — 404).

### Ручне тестування відгуків

Щоб не чекати дати повернення, оплачене замовлення можна провести до «Документи готові» через
API менеджера (`take` → `confirm` → документ-ваучер → `documents-ready`), а потім завершити його
одразу (лише для розробки; інші статуси команда відхиляє):

```powershell
python -m scripts.complete_orders --order-id 42 --force
```

Замовлення стає «Завершено» від імені Системи (запис в історії й сповіщення клієнту — як
звичайно), після чого клієнт може залишити відгук, а менеджер — його модерувати.

## Адміністрування

Роль `admin` (ТЗ 4.3, 4.5.8). Адміністратор **не** обробляє замовлення, повернення, платежі,
відгуки й промокоди (розподіл обов'язків, ТЗ 7) — там він отримує 403.

**Користувачі** (`/api/admin/users`): список (фільтри `role`, `is_active`, пошук `q` за ім'ям,
телефоном, e-mail), створення співробітника (`manager`, `finance`, `admin`) з початковим паролем,
`PATCH` — роль (лише між ролями співробітників; клієнт лишається клієнтом), блокування
(`is_active`), ім'я, e-mail, телефон; `POST /{id}/reset-password` — новий пароль.

- Адміністратор не може заблокувати себе чи змінити собі роль; останнього активного
  адміністратора не можна заблокувати або понизити.
- Блокування і зміна ролі діють одразу (користувач читається з БД при кожному запиті).
  Після скидання пароля старі токени не приймаються (`users.tokens_valid_after`, з точністю до
  секунди, як `iat` у JWT); вхід з новим паролем працює одразу.
- Видалення користувачів немає — лише блокування (історія зберігається).

**Довідники** (`/api/admin/countries|cities|resorts|hotels|insurance-types|transfer-types`):
список (разом з архівними), створення, редагування, `POST /{id}/archive` і `/restore`,
`DELETE` — лише якщо на запис ніщо не посилається (інакше 409 з переліком, де він
використовується). Архівний запис зникає з публічних списків і з вибору для нових турів і
замовлень, але лишається в наявних; архівна країна приховує свої курорти, готелі й міста.
Тип страхування і трансферу «за замовчуванням» — завжди рівно один. Рейтинг готелю тут лише
для читання (рахується з відгуків). Мови сайту — `/api/admin/languages` (українську вимкнути не можна).

**Налаштування** (`GET/PUT /api/admin/settings`, форма 4.6.4.1): курси EUR і USD (UAH = 1),
відсоток еквайрингу, таймаут бронювання (хв), утримання місць при переказі (год),
премодерація відгуків, системний e-mail, технічні роботи, **телефон і e-mail служби підтримки**
(порожнє значення прибирає контакт; публічно — `GET /api/site/contacts`, також під час
технічних робіт: їх показують футер і «Забули пароль?»). Змінюються лише передані поля,
діапазони перевіряються. Нові значення діють одразу для нових розрахунків; ціни вже оформлених
замовлень не змінюються (зафіксовані при оформленні).
`GET /api/admin/payment-gateway` — що налаштовано для платежів (без ключів: ключі лише в `backend/.env`).

**Технічні роботи.** Поки увімкнено, усі запити отримують **503** «Тривають технічні роботи»,
крім: `/health`, документації API, `POST /api/auth/login` (клієнт отримує 503 замість токена,
співробітники входять), `GET /api/auth/me` для адміністратора, `/api/admin/...` і вебхука Stripe
(оплати, що вже надійшли, обробляються). Фонові задачі Системи працюють далі.

**Журнал змін** (`GET /api/admin/audit-log`, фільтри `user_id`, `entity`, `entity_id`, `action`,
`date_from`/`date_to`): хто що змінив, старе → нове значення. Пишуться всі зміни
адміністратора і промокодів; паролі, ключі й токени не записуються ніколи. Таблиця
`audit_log` лише доповнюється: тригер у БД забороняє `UPDATE` і `DELETE` (ТЗ 7).

**Промокоди** (роль `manager`, `/api/manager/promo-codes`, форма 4.6.2.3): код 4–20 латинських
літер і цифр (унікальний), знижка 1–100 % або фіксована в гривнях, мінімальна сума, дати дії
(кінець пізніше за початок), ліміт використань, «Активний». `used_count` і `paid_count` —
лише для читання. Використаний промокод не видаляється і не перейменовується — лише деактивується.

## Фронтенд

Публічна частина сайту — React-застосунок у `frontend/` (Vite, TypeScript strict, antd 6,
React Router, TanStack Query + axios, react-i18next). Потрібен Node.js 22.12+.

```powershell
cd frontend
npm install
copy .env.example .env.local   # VITE_API_URL=http://localhost:8000 — адреса бекенду
npm run dev                    # http://localhost:5173 (бекенд має працювати на :8000)
```

| Команда | Що робить |
|---|---|
| `npm run dev` | сервер розробки на http://localhost:5173 |
| `npm test` | тести (Vitest + Testing Library, запити до API підмінені) |
| `npm run build` | перевірка типів (`tsc -b`) і збірка в `frontend/dist` |
| `npm run typecheck` | лише перевірка типів |
| `npm run lint` | oxlint |
| `npm run gen:api` | згенерувати типи API `src/api/schema.d.ts` з `http://127.0.0.1:8000/openapi.json` |

- **Типи API не пишуться вручну:** після кожної зміни схем бекенду — `npm run gen:api` (бекенд
  має бути запущений) і закомітити `schema.d.ts`. Адреса `127.0.0.1`, а не `localhost`: на Windows
  Node може звернутися до IPv6 `::1`, а uvicorn слухає лише IPv4.
- **CORS:** бекенд приймає запити лише з адрес у `CORS_ORIGINS` (за замовчуванням
  `http://localhost:5173` і `http://127.0.0.1:5173`), тому Vite запускається строго на порту 5173.
- **TypeScript 6, а не 7:** TypeScript 7 не має JS API компілятора, без якого не працює
  openapi-typescript (issue openapi-ts/openapi-typescript#2841). openapi-typescript 7.13.0 оголошує
  peer `typescript ^5.x`, тому в `package.json` є `overrides`; результат генерації з TS 6.0.3 і 5.9.3
  перевірено — однаковий.
- **openapi-typescript у режимі підтримки:** автор оголосив 19.09.2026, що пакет більше не
  оновлюватиметься, навіть виправленнями безпеки (issue openapi-ts/openapi-typescript#2874).
  Це інструмент лише для розробки: він генерує `.d.ts` і не потрапляє в збірку сайту, тому версія
  закріплена точно (`7.13.0`). Не плутати з дорожньою картою на 2026 рік (discussion #2559), де
  в режим підтримки перевели `openapi-fetch`, `openapi-react-query` та `openapi-metadata`.
- **Дизайн:** палітра «Море і пісок» (`src/theme.ts`), без анімацій (`motion: false`) і без емодзі,
  контраст тексту не нижче 4.5:1 — це перевіряє тест `src/theme.test.ts` на реальних токенах antd.
- **Тексти** інтерфейсу — лише через ключі `src/i18n/uk.json` (ключі перевіряє TypeScript).

**Каталог `/tours`** (`docs/frontend/01-catalog-page.md`): пошук за назвою, країна, курорт,
місто вильоту, транспорт, дати виїзду, кількість ночей, ціна, зірковість, харчування, «лише з
вільними місцями»; сортування за датою, ціною, рейтингом і назвою (А–Я); 12 турів на сторінку.
Увесь стан — у рядку адреси (`?country_id=4&stars=4&stars=5&meal_plan=ai&page=2`): посилання
відкривається в новій вкладці з тими самими результатами, «Назад» повертає попередній пошук.
«Найближчий виїзд» — найближча дата, на яку ще можна забронювати: від завтра за київським
часом, як і правило бекенду.

**Сторінка туру `/tours/:id`** (`docs/frontend/02-tour-details-page.md`):
- «хлібні крихти»: «Каталог» повертає до тих самих фільтрів, з яких прийшли;
- галерея з переглядом на весь екран (кожне фото — кнопка, працює з клавіатури);
- вкладки в адресі (`?tab=program|hotel|reviews`, зміна вкладки не додає запис в історію, тож
  «Назад» веде одразу в каталог): «Опис» із «Що включено / не включено», «Програма» по днях,
  «Готель» — таблиця лише заповнених фактів, «Відгуки (N)» — вантажаться тільки при відкритті,
  по 10 на сторінку, з фото;
- блок бронювання: ціна за дорослого й дитини, дата виїзду від завтра (Київ), харчування,
  вільні місця; на телефоні — панель із ціною та кнопкою внизу екрана. «Забронювати» веде
  на заглушку `/booking/:tourId?date=…` (лише для клієнта) — через
  `src/features/booking/startBooking.ts`: гість спершу потрапляє на вхід і повертається сюди;
- тур, що більше не продається, і неіснуючий тур — сторінка 404.

**Вхід і реєстрація** (`docs/frontend/03-auth-pages.md`):
- `/login` — «Номер телефону або e-mail» і пароль; `/register` — поля форми 4.6.1.1 з тими самими
  правилами, що й на бекенді, автоматичний вхід після реєстрації. Після входу — на `?redirect=`
  (лише внутрішні адреси, напр. бронювання), інакше клієнт — у «Мої замовлення», персонал — у
  «Робочий кабінет» (`/office`, поки заглушка).
- Токен зберігається в `localStorage` (переживає перезавантаження, спільний для вкладок).
  Ризик: скрипт, впроваджений на сторінку (XSS), міг би його прочитати — React екранує вивід,
  сторонніх скриптів немає, токен живе 60 хв. Refresh-токена бекенд не видає: якщо сервер
  відхилив токен (минув час, акаунт заблоковано, адміністратор скинув пароль) — вихід і сторінка
  входу з повідомленням «Сеанс завершився. Увійдіть знову.» і поверненням на ту саму сторінку.
- Помилки: під полем (зокрема помилки сервера 422 і зайнятий телефон чи e-mail), загальні — в
  `Alert` над кнопкою; технічні тексти бекенду не показуються (одна таблиця
  `src/features/auth/authErrors.ts`). 429 («Забагато спроб входу») уже обробляється — на
  майбутнє обмеження спроб входу.
- Відновлення пароля через e-mail ще немає (потрібна розсилка): «Забули пароль?» показує
  контакти підтримки з налаштувань — пароль скидає адміністратор.
- Кнопка «Як це працює?» у правому нижньому куті відкриває короткий посібник для сторінки.

`feature/frontend-auth`, у репозиторії їх немає): клієнт `client-test@example.com` /
`+380990000001`, пароль `Test-client-1`; менеджер `+380990000002` (`scripts.create_user`),
