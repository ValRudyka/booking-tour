# CLAUDE.md — Tour website (course project)

Solo course project: a tour company website with catalog, online booking, Stripe test-mode
payments, manager processing, refunds and reviews. The full requirements are in the
technical specification (ТЗ): `docs/tz/TZ_tour_website_v2.md` (Markdown, searchable) and
`docs/tz/TZ_tour_website_v2.docx` (the official document). **Read the relevant ТЗ section
before implementing a feature** — section numbers are referenced throughout the code.

The owner is a student (Python/SQL confident, React intermediate) who must defend the
project: explain non-obvious decisions briefly in code comments and PR descriptions.

## Working rules (from the owner — follow them)

- **Do everything the ТЗ describes**, in the backlog order below. Do not drop features
  because of deadlines; a working end-to-end demo must exist after every merged feature.
- **Check the official documentation of each library before using it** (APIs change;
  e.g. FastAPI now recommends `pwdlib` + `PyJWT`, not passlib/python-jose).
- **Branches:** Git Flow. `main` (releases, tagged `vX.Y.Z`), `develop` (integration),
  `feature/<name>` — **one branch per feature, not per change**. Small fixes: `fix/<name>`.
  Branch from `develop`, merge back via a Pull Request into `develop`.
- **Commits:** at least one commit per fix/change, but no micro-commits. Conventional
  Commits: `feat(scope): ...`, `fix(scope): ...`, `test(scope): ...`, `docs: ...`,
  `chore: ...`, `build: ...`, `refactor: ...`.
- Ask before decisions that are hard to undo (schema changes to existing data, deleting
  branches, force-push).
- UI and API error messages in **Ukrainian**; code, comments, logs in **English**.

Conventions:
- Enums are stored as `VARCHAR + CHECK` (`str_enum()` in `models/base.py`), values are
  lower-case English codes; Ukrainian labels live in the frontend.
- Money: `Numeric(12,2)`; rates `Numeric(12,4)`. Order price and `rate_used` are frozen at
  checkout.
- All order status changes go through `services/order_status.py: change_status()` — it holds
  the full ТЗ 4.4.1 transition table, writes `order_status_history` (`changed_by = NULL` means
  the System) and does the quota accounting (-> paid: seats_sold += tourists after re-checking
  free seats; paid states -> rejected/cancelled: seats back). **Never assign `order.status`
  directly.** Who may make a transition is checked by the calling service.
- Seat quota (`services/seats.py`): free seats = `seats_total − seats_sold − seats in unexpired
  holds` (checkout/awaiting_payment with `hold_expires_at > now`); lock the tour row
  (`lock_tour()`, `SELECT ... FOR UPDATE`) when holding/selling seats. The hold lasts
  `booking_timeout_min` (settings, default 20) from order creation; edits and confirm never
  extend it. Only a bank transfer does: once when it is chosen and again after each partial
  payment, to `bank_transfer_hold_hours` (settings, 48) from that moment (`extend_hold()`,
  logged in `audit_log`). Partly paid orders are never cancelled automatically.
- Expired holds: `services/order_expiry.py: expire_orders()` cancels them as the System; it runs
  every `ORDER_EXPIRY_INTERVAL_SEC` (60; 0 = off, as in tests) from the FastAPI lifespan, and
  via `scripts.expire_orders`. An order touched after its hold ran out is cancelled on the spot.
- Order price (`services/pricing.py`) is Decimal with ROUND_HALF_UP; `total_uah`,
  `discount_uah`, `rate_used` are recalculated only in checkout and at confirm, then frozen.
- Files: only `uploads/tours` (tour photos) is public, mounted at `/uploads/tours`. Never
  mount `upload_dir` itself. Order documents and any personal files (vouchers, tickets,
  passport scans, receipts) are stored **outside** the public folder (e.g.
  `upload_dir/private/...`) and downloaded **only** through an endpoint that checks the user's
  rights (the order's client or staff with the right role). File names on disk are always
  generated by the server, never taken from the client.
- Payments (`services/payments/`): the app talks only to `PaymentGateway` (`get_gateway()`:
  `StripeGateway` with `StripeClient`, or `MockGateway` without network; tests always mock).
  A card payment is a `payments` row + Checkout Session; the order becomes `paid` **only** from
  the signed webhook. Idempotency: payment row `FOR UPDATE` + forward-only payment states
  (pending -> succeeded | failed) + refund rows/idempotency keys; no events table. Every money
  movement is its own row (partial bank transfers too). Order `payment_status` is set together
  with `change_status` in `apply_received_money()`. `payments.origin`: `app` (real or Stripe test
  money, mock gateway, bank transfer) or `demo_seed` (written by `scripts.seed_demo`, no money
  moved). The finance register returns it and filters `?origin=`; **reports must count only `app`**.
- Notifications (`services/notifications.py`): `change_status()` itself notifies the client of
  every client-visible transition (not of the client's own actions); pass the manager's text as
  `client_message`. Staff get `notify_managers()` / `notify_finance()`. In-app only (table
  `notifications`, `GET /api/me/notifications`); e-mail is `feature/notifications-email`.
- Manager processing (`services/order_processing.py`): `take` sets `orders.manager_id`; after
  that only that manager may change the order (409 for others), every manager may view it;
  hand-over via `assign` (audit_log), only from `paid` on and not archived (`ASSIGN_STATUSES`).
  Two managers taking at once: `lock_order()` (`FOR UPDATE`) serialises them, the second gets 409
  «Замовлення веде інший менеджер (…)».
- Staff actions (`services/staff_actions.py`, spec 09): the staff order card carries
  `staff_actions: [{action, allowed, reason}]` (`StaffAction`). An action is listed only in the
  statuses its endpoint accepts (the status tuples of `order_processing` / `order_documents`);
  `allowed`/`reason` come from the same refusal functions the endpoints raise with
  (`owner_refusal`, `documents_ready_refusal`, `archive_refusal`, `order_documents.upload_refusal`).
  Documents carry `can_delete` (`delete_refusal`). Finance gets `[]` until spec 12.
  `GET /manager/orders`: `queue=new|mine|all` (new = paid and nobody responsible) with
  `queue_counts` that ignore the search filters, `client`, `created_from/to` (Kyiv days), `sort`;
  `GET /manager/managers`, `GET /manager/orders/document-rules`. Order documents (`services/order_documents.py`) are private
  files `upload_dir/private/orders/<id>/`; the client sees trip documents from `confirmed` on,
  `cancel_evidence` (client's files for a cancellation request) is staff-only.
- Tour management (spec 10, `services/tours.py`, `services/tour_actions.py`):
  - One tour = **one date range** (`departure_from..departure_to`, any start date inside it) with
    one nights value, one price pair and one quota (form 4.6.2.1, field 10). Another price period
    is a copy of the tour.
  - `tour_actions` (`TourAction`: edit, publish, unpublish, archive, restore, copy) like
    `staff_actions`: listed by status (`ALLOWED_TRANSITIONS`), `allowed`/`reason` from the
    endpoints' own refusals (`edit_refusal`, `publish_refusal`, `archive_refusal`). Only a draft
    is edited (ТЗ 4.4.1); archived → draft is «Відновити» (audited).
  - `locked_fields`: `LOCKED_FIELDS` (titles, hotel, dates, nights, transport, departure city,
    meal plan — what order pages read live until `feature/order-snapshot`) are locked while an
    order of the tour was **ever paid** (`paid` in its history) or a booking is **active**
    (checkout / awaiting_payment with an unexpired hold, or a partly paid transfer). PATCH may send
    them unchanged; a change is 409 with `loc`. Prices stay editable (orders freeze theirs).
  - Unpublish keeps active bookings payable (`confirm_order` accepts a draft tour for an existing
    checkout order). Archive cancels the unpaid bookings like the expiry job (sessions closed,
    clients notified, numbers in the tour's audit entry; a late card payment is refunded by the
    webhook) and is refused while a transfer is partly paid. The dialogs show `active_bookings` /
    `archive_cancels` from the API.
  - Quota ≥ seats sold + seats in unexpired holds. Copy takes the new range in the body
    (`TourCopyIn`), «Копія — …», not featured. Field errors carry `loc` (422 `type: "tour_rule"`).
    An edit keeps the tour's own archived hotel / city; publishing re-checks them.
  - `GET /manager/tours`: `q`, `status`, `country_id`, `resort_id`, `departure_from/to` (range
    overlap), `sort=updated_desc|departure_asc|title_asc`; `GET /manager/tours/rules` (photo and
    text limits).
- Refunds (`services/payments/refunds.py`): refund rows point at their payment (`refund_of_id`);
  amount = succeeded payments − live refunds − ФПВ (`orders.fpv_uah`), split newest payment first.
  Stripe parts use the key `refund-<payment id>-<n>` (n = refund rows of that payment + 1); the
  whole refund runs in a savepoint, so if a later Stripe part fails nothing is recorded and the
  same request is repeated (Stripe replays the parts already made). A refund is finished when no
  row is pending and only the ФПВ is kept: then payment_status and `cancel_requested -> cancelled`.
  Webhooks `refund.updated` / `refund.failed` (failed can follow succeeded) — `handle_refund_event`.
  The manager may archive rejected/cancelled orders only when `refund_finished()`.
- Business dates: "today" is **always** the Kyiv date from `services/clock.py` (`today()`,
  `tomorrow()`, `day_start(d)` for filtering UTC timestamps by Kyiv days; `now()` is the one
  place tests patch). Never `date.today()` or a naive `datetime.now()` in `app/`:
  `tests/test_business_dates.py` scans for them. Date filters (finance register, audit log) use
  Kyiv days. The completion job (`services/order_completion.py`) completes `documents_ready`
  orders with `end_date < today`; orders that never got documents are only reported
  (`?overdue=true` in the manager list).
- "For sale" = `status = active` and a start date from **tomorrow** (Kyiv) remains
  (`departure_to >= clock.tomorrow()`), the same rule as the order start date. On its last start
  day a tour leaves the catalog and its page is 404; publishing needs such a date too. So pages
  about past trips (client's orders) must show the data stored with the order, not `/tours/:id`.
- Catalog extras (feature/catalog-improvements):
  - `tours.meal_plan` (`MealPlan`: ro/bb/hb/fb/ai/uai, nullable, on the tour, not the hotel);
  - `tours.included` / `excluded` (TEXT[]). Insurance and transfer never go in `included`: they
    are chosen at checkout;
  - hotel facts (`beach_line`, `distance_to_beach_m`, `distance_to_airport_km`, `check_in`,
    `check_out`, `amenities`, `room_types`; form 4.6.4.2, admin reference). Only the tour page
    returns them (`HotelDetailOut`); cards keep `HotelOut`;
  - lists are cleaned by `services/text_lists.py` (at most 20 items of 200 characters);
  - `sort=title_asc` uses `COLLATE "uk-x-icu"`. **The database needs ICU**: migration
    `c3d8a1f5b742` stops with a message without it.
- Demo seed provenance (`scripts.seed_demo`, dev only):
  - resorts and hotels = audit «created» by the seed admin;
  - tours and promo codes = `created_by` the seed manager;
  - tour photos = audit «tour_image created» by the seed manager;
  - past trips = orders of the 4 blocked seed clients (`seed-client-N@tour.local`), payments
    `origin=demo_seed`.
  - `--reset` deletes exactly these (orders too, audited) and archives anything other people use.
- Reviews (`services/reviews.py`): status `pending -> published | rejected`, `published ->
  rejected` (unpublish), `rejected -> pending` once (client's PATCH, `resubmitted_at`). Only for
  completed orders (or archived after completed); `reviews.hotel_id` is saved when written. Staff
  only publish/reject, never edit. Every publish/unpublish calls `recalc_hotel_rating()` in the
  same transaction (hotel row locked; AVG of published, 2 places, NULL if none). Setting
  `review_premoderation` (default true). Photos: private `upload_dir/private/reviews/<id>/`,
  served by `/api/reviews/{id}/photos/{pid}` — public only when published, else the author and
  managers (404 for others; `OptionalUser` dependency). Public schemas carry no personal data.
- Administration (role admin; never order processing, refunds, payments, moderation or promo
  codes — ТЗ 7 separation of duties, tested in `test_separation_of_duties.py`):
  `services/admin_users.py` (staff only via admin; roles change only between staff roles; no
  self-block/self-demote; the last active admin stays — admin rows locked before counting;
  a client's personal data is not edited by the admin; the admin reset refuses your own password;
  blocking also sets `tokens_valid_after`; `POST /admin/users` without `password` generates a
  temporary one, answered once in `temporary_password`, never stored or audited;
  `GET /admin/users?staff=true|false`),
  `services/reference_admin.py` (archive/restore; archiving a hotel, resort, country or departure
  city is refused while a published tour uses it — the catalog does not read `is_archived`;
  DELETE only when `references()` finds nothing, the refusal names the rows in Ukrainian;
  exactly one default insurance/transfer type, partial unique index), `services/settings_admin.py`
  (form 4.6.4.1 plus `support_address` and `maintenance_message`, key/value rows, no migration;
  `rules()` and `limits()` for the form; keys stay in .env, only `gateway_status()`),
  `services/maintenance.py` (app-wide dependency; open list in its docstring; the 503 text is the
  admin's `maintenance_message` or the default).
- Admin actions (`services/admin_actions.py`, spec 13, the `staff_actions` pattern): every admin
  user carries `user_actions` (edit, change_role, block, unblock, reset_password) and every
  reference record / language `admin_actions` (edit, archive, restore, delete, make_default,
  enable, disable), each `{action, allowed, reason}` from the refusal functions the endpoints
  raise (`edit_refusal`, `role_refusal`, `block_refusal`, `reset_refusal`, `archive_refusal`,
  `restore_refusal`, `delete_refusal`, `default_refusal`, `language_*_refusal`); a list reads
  its counts in grouped queries (`refusal_context()`). The audit log answers `user_name` /
  `user_role`. Tokens carry `iat`; `users.tokens_valid_after` (whole
  seconds, `token_cutoff()`) is set on admin password reset; `user_from_token()` checks it.
- Audit: every admin change and every promo code change calls `services/audit.py: audit()` with
  old/new values; fields named like password/secret/key/token/hash are dropped. Every audit row
  goes through `audit()` (never `db.add(AuditLog(...))`), so that filter always applies. `audit_log` is
  append-only (DB trigger refuses UPDATE/DELETE).
- Promo codes are managed by managers (`services/promo_admin.py`, `/api/manager/promo-codes`);
  a code used by any order cannot be deleted or renamed, only deactivated.
- Checkout API details (feature/frontend-checkout):
  - `DomainError(loc=...)`: the tourist rules of `services/orders.py` name the field
    (`["body", "tourists", i, field]`); the orders router then answers in FastAPI's 422 shape

  - `PATCH /api/orders/{id}` with `tourists: []` clears the list (to change the numbers later).
  - `GET /api/orders/{id}` returns `price`, calculated on read and never saved: the current

  - `GET /api/orders?group=all|active|completed|cancelled` (`OrderGroup`): archived goes by

  - `GET /api/orders/{id}` adds `tour_for_sale` (`catalog.is_for_sale()`, same rule as the
    catalog query), country, resort, departure city, transport, meal plan (live from the tour row,

  - Form rules come from the server: `GET /orders/{id}/cancel-request` (evidence count / MB /

## Payment rules (implemented in feature/stripe-payments)

- Stripe Checkout Session `expires_at` must be 30 min–24 h after creation, but our hold is
  `booking_timeout_min` (20). So when `expire_orders` cancels an `awaiting_payment` order that
  has a Stripe session, it must expire that session via the Stripe API
  (`POST /v1/checkout/sessions/{id}/expire`), otherwise the client could still pay.
- If a successful payment still arrives for an order that is already cancelled (race at the
  deadline), refund it automatically and do not change the order status.
- Moving to `paid` must re-check free seats under the tour row lock; `seats_sold` must never
  exceed `seats_total` (`change_status()` already does this and raises 409 if seats are gone —
  that case must also lead to an automatic refund).
- Return URLs (`service.py: return_urls(order)`, feature/frontend-checkout):
  `{FRONTEND_URL}/payment/success?order_id=…&session_id={CHECKOUT_SESSION_ID}` and
  `/payment/cancel?order_id=…`. Coming back changes nothing; the success page waits for the
  webhook. `config.py: check_startup_settings()` (app lifespan) refuses production without
  `FRONTEND_URL`. The old `GET /api/payments/result` stays for support.
- Mock gateway page: «Оплата успішна» / «Сесія минула» with `?return_to_site=1` redirect (303) to
  the success / cancel URL like Stripe; without it they answer JSON (tests).

## Frontend

Lives in `frontend/` in this repository (same Git Flow branches as the backend).

- **Stack:** React 19 + TypeScript + Vite; React Router; TanStack Query for server state with
  axios as the HTTP client; react-i18next (Ukrainian first: `uk.json`, `en.json` in
  `feature/i18n-en`); API types generated from FastAPI `/openapi.json` with `openapi-typescript`
  (regenerate after every backend schema change — never hand-write API types).
- **TypeScript 6, not 7:** TS 7 ships no JS compiler API and openapi-typescript needs it
  (upstream issue #2841). openapi-typescript 7.13.0 declares a peer of `typescript ^5.x`, so
  `package.json` has an `overrides` entry; its output with TS 6.0.3 was diffed against 5.9.3 and is
  identical. `strict` is set explicitly in `tsconfig.app.json`.

  updates, security fixes included; not the 2026 roadmap discussion #2559, which put openapi-fetch,

    `Intl.NumberFormat` (`utils/format.ts`), never used in float arithmetic.

  - i18n keys are type-checked.

    accessible names.

## Domain cheat-sheet

Roles: `client`, `manager`, `finance`, `admin` (ТЗ 4.3). Staff are created by the admin /
`scripts.create_user`, never self-registered.

Order statuses (ТЗ 4.4.1): `checkout → awaiting_payment → paid → in_progress → confirmed →
documents_ready → completed → archived`; `in_progress → rejected` (full refund);
`paid..documents_ready → cancel_requested → cancelled` (refund minus ФПВ);
`checkout/awaiting_payment → cancelled` on timeout (`booking_timeout_min`, default 20).
Payment status (separate field): `awaiting, partially_paid, paid, partially_refunded, refunded`.
Tour status: `draft ↔ active → archived`.

Price (form 4.6.1.2, field 8): `(base_price × adults + child_price × children) × rate +
insurance × tourists + transfer − promo discount`, child = under 12 at tour start,
`child_price NULL` = base price.
